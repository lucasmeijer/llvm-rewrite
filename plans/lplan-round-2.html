1Several attempts in one repo, sharing one harness and one test corpus

Layout: harness/, tests/, knowledge/ and the skills are shared. Each attempt is a self-contained impl/<lang>/ with its own build script. Each one produces three binaries, impl/<lang>/bin/{opt,llc,llvm-link}, with the command line agreed in decision 5. The harness takes --impl <lang>. A test written while working on one attempt is immediately available to all the others. The first three attempts are C (C11), Rust and Zig. They start in parallel once the harness and layer 0's test corpus exist.

Why these three languages, and why one repo?

All three can be written in a data-oriented style, and they cover the range of how much the language helps: C gives nothing and takes nothing away; Rust gives memory safety but pushes back on index-heavy mutable designs, so it's interesting to see whether that helps or hurts; Zig has data-oriented idioms built in (MultiArrayList, allocators passed explicitly, comptime) and its own compiler is a well-known example of the style. One repo means one test corpus and one scoreboard, so harness status --all compares the attempts directly. It also means a fact one attempt learns about LLVM benefits the others.

Starting only after the harness exists means no attempt invents its own testing setup.

Alternatives:

  1. Odin instead of Zig: designed explicitly for data-oriented programming (SoA built into the language), but agents have less training data for it.
  2. Jai as one of the attempts, if your compiler beta can be installed in the workspaces.
  3. One repo per attempt, with the harness and tests as a git submodule: the attempts are better isolated, but sharing tests and knowledge gets awkward.
  4. Start with one attempt through layer 1, then fork the others: the harness gets more shakedown first, at the cost of slower comparison between attempts.

2Data-oriented rules, the same for every attempt

docs/data-oriented-design.md is binding for every attempt:

  • No classes, inheritance, virtual dispatch, trait objects or visitor patterns. Plain structs and free functions, and passes are functions over the module's tables.
  • Entities (values, instructions, blocks, functions, types, uses) are rows in arrays, referenced by 32-bit indices, never by pointers. Instruction kind is an enum tag, dispatched with a switch.
  • Hot data goes in structure-of-arrays form; variable-length operands live in shared side arrays, addressed by (start, count).
  • Allocation happens in arenas per module and per pass, with no allocation per node. Types and constants are interned once.

Each attempt chooses its own concrete layout and documents it in impl/<lang>/DESIGN.md.

How do we copy LLVM's behaviour exactly without copying its object structure?

LLVM's output depends on things that look like implementation details. Use-lists are ordered (a new use is pushed onto the front of the list). InstCombine visits its worklist in a particular order, and so do RAUW and value-name uniquing (%x.1). The order in which IR folds constants also shows in the output. An IR that's identical on every pass has to reproduce those observable orders, so each attempt's design doc must state how its tables preserve them. This is the most likely place where data-oriented design and exact output collide, and the design docs are where the attempts will differ most.

Each attempt choosing its own layout is what makes several attempts worth having. The shared rules keep them all honestly data-oriented.

Alternatives:

  1. One shared reference layout (an exact table schema) that every attempt implements: easier to compare, less to explore.
  2. Rules only, with no per-attempt DESIGN.md.
  3. Stricter rules: no methods at all (Rust impl blocks only for trivial accessors), and every hot table must be SoA.

3IR must match exactly all the way up to instruction selection

Exact matching of IR covers everything up to the input of instruction selection, not just opt. At -O2, llc also runs IR→IR passes before isel (loop-strength-reduce, codegenprepare, expand-memcmp, atomic-expand, partially-inline-libcalls…). Those get pass tests too, run with -mtriple=x86_64-unknown-linux-gnu. Our llc must accept -print-before=x86-isel (or an equivalent dump), and the harness compares that IR against LLVM's for every e2e test. Only what happens after that point is judged by running the program.

Why draw the line at isel and not at the end of opt?

If the boundary were the end of opt, llc's IR passes would sit in a blind spot: their bugs would only show up as wrong program output, deep inside a backend we're allowed to do differently. Moving the line to isel makes "everything we compare exactly is IR" literally true. It also gives each e2e test a second, stronger check: the IR entering isel must match, and the program must behave the same. The exact flag for capturing pre-isel IR from LLVM 23's x86 backend gets confirmed during bootstrap.

Alternatives:

  1. Boundary at the end of opt, with llc's IR passes treated as part of the backend.
  2. Also require exact matches for the generic machine IR (MIR) after IRTranslator: stricter, but it locks us into LLVM's isel structure.
  3. Only compare the pre-isel IR when a test asks for it, not for every e2e test.

4Python harness, live oracle with a cache, and a passing list per attempt

harness/ is plain Python 3 (standard library only), driving binaries as subprocesses. Following your choice of 6A, LLVM's outputs are computed live and cached in .cache/oracle/, keyed by a hash of (input, command, LLVM version). Since status now depends on the attempt, the in-file STATUS: is dropped. Instead each attempt has impl/<lang>/passing.txt (sorted). harness check --impl X fails if a listed test fails, and --update adds tests that have started passing. Pending = in the corpus but not in the list.

Why Python and not one of the attempt languages?

The harness has to be neutral between attempts and readable by every agent, and all it does is orchestrate subprocesses. Python needs no build and is already installed. A standard-library-only rule means there's nothing to set up. With the cache, a re-run only invokes LLVM for tests that are new or have changed, so the pre-push check stays fast. Sorted lists in separate files per attempt mean agents on different attempts never touch the same file. Two agents on the same attempt usually add lines in different places, which git merges cleanly, and the rule on conflicts is "take the union, re-run".

Alternatives:

  1. Write the harness in Rust: faster and typed, but it then leans toward one of the attempts and needs a build.
  2. A single status.tsv file with a column per attempt: one table, but every agent edits the same file.
  3. No cache: simpler, but every check re-runs LLVM on every test.

5Push straight to main, enforced by a local pre-push hook

An agent pushes to origin main (lucasmeijer/llvm-rewrite, using it only as a git remote) when a unit of work is complete. The protocol: commit, git pull --rebase, run harness check on the rebased tree for every attempt the commit touches, then push. If someone else pushed in the meantime, repeat. A versioned .githooks/pre-push hook runs the same check. scripts/setup.sh sets core.hooksPath, so the ratchet holds even without CI. Who does which unit is up to the loop you're designing. docs/roadmap.md lists the units for each layer, and an agent ticks one off in the same commit that completes it.

Why a hook, and why should shared changes check every attempt?

Without CI, the only thing between a regression and main is the agent's own discipline. A hook turns that into a mechanism. A commit that changes only impl/zig/ needs only the Zig check. A commit to harness/ or tests/ can break other attempts' ratchets (for example a new test whose oracle input crashes the harness), so those commits run every attempt's check.

Alternatives:

  1. A bare repo in /persistent as the shared remote, so nothing touches GitHub at all.
  2. No hook, just the instruction in AGENTS.md.
  3. Shared-file commits check only the current attempt; other attempts repair their own ratchet when they next pull.

6Three places for notes: knowledge about LLVM, notes per attempt, and challenge reports for you

knowledge/llvm/<area>.md          facts about LLVM behaviour, shared by all attempts
impl/<lang>/NOTES.md              findings specific to one attempt or language
reports/challenges/<date>-<lang>-<slug>.md   one file per challenge, for you

knowledge/ is organised by topic (instcombine.md, use-list-order.md, sysv-abi.md…). It holds things like "opt infers nofree here because…", and agents read the relevant file before they start work in that area. reports/challenges/ is about the process, not the compiler: unclear instructions, a harness that was slow or misleading, a unit that was too big, where the agent got stuck or had to guess. Each file has fixed fields: what happened · time/effort lost · what would have helped. Before an agent pushes a unit, it writes a challenge report if anything got in its way.

Why one file per challenge but one file per topic for knowledge?

Many agents write challenge reports at the same time, and appending to a single shared file conflicts on every rebase. One file per report never conflicts, and you can sort and grep them by date and attempt when you tune the loop. Knowledge is meant to be curated, not appended: an agent edits the topic file and corrects stale claims. Topics rarely collide, and grouping by topic is what makes it findable. When a knowledge topic settles, it can be promoted into a skill.

Alternatives:

  1. One file per finding for knowledge too (no conflicts, but a pile of files nobody reads).
  2. Single append-only FINDINGS.md and CHALLENGES.md at the root.
  3. Add a third report type, reports/units/, a short summary of each completed unit (time taken, tests moved), giving your loop a progress log.

7LLVM 23.1.5 from the official release tarball, fetched by a script

The latest official release is LLVM 23.1.5 (published four days ago). scripts/fetch-llvm.sh downloads LLVM-23.1.5-Linux-X64.tar.xz from the GitHub release (about 2 GB, signature checked) into gitignored third_party/llvm/, and does a sparse checkout of the source at llvmorg-23.1.5 (llvm/lib, llvm/include, llvm/test) for reading. Everything uses that clang (including generating tests) and those tools. The harness refuses to run against any other version. Moving to a newer release is a deliberate, separate unit of work.

Why not apt.llvm.org, or a source build?

The official tarball is exactly "the release", needs no root, and works the same in every workspace. apt.llvm.org packages are built from snapshots and get patched by distributions. A source build with assertions on is still a good later addition (alternative 1C from round 1). Bootstrap checks that the tarball contains everything the harness needs (opt, llc, llvm-as, llvm-dis, llvm-link, llvm-reduce).

Alternatives:

  1. Use the apt.llvm.org llvm-23 packages.
  2. Build from source with assertions, and keep the result in /persistent so workspaces can share it.
  3. Keep the tarball in /persistent too, so new workspaces skip the 2 GB download.
