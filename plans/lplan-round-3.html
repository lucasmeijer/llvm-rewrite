1I do the bootstrap myself in this workspace, before any attempt starts

One sequence, pushed to main as I go:

  1. .agents-in-the-cloud/Dockerfile, verified by building it here.
  2. The harness, with all four test kinds working against LLVM itself. As a self-test, I point --impl at LLVM's own binaries, which must pass 100%.
  3. A starter corpus: about 150 C snippets compiled to IR at -O0 and -O2, about 20 function tests, a small batch of tests imported from LLVM's own Transforms tests, plus the importer script.
  4. AGENTS.md, the four skills, docs/roadmap.md, the knowledge/reports skeleton, and empty impl/{c,rust,zig}/ folders.

Then you start the attempt agents with your loop.

Why not let the first agents of each attempt bootstrap together?

Everything shared has to be in place and stable before three attempts start pushing to the same main: the harness's command line, the test format, the oracle and the layout. If it changes underneath running attempts, each change means churn in three places. Self-testing against LLVM's own binaries proves the harness and every test are sound before an agent ever reads a failure and blames its own code. That matters most when the harness is the only judge.

Alternatives:

  1. I build the harness and Dockerfile only. Agents grow the corpus as their first units.
  2. Bootstrap through layer 0 of one attempt as well, so the end-to-end flow is shaken out on real code first.
  3. Spread the bootstrap across a few parallel agents (harness, corpus, docs), which you'd explicitly ask me to run.

2A unit of work is defined by the tests it must make pass

Each unit in docs/roadmap.md has an ID, a short description, its dependencies, and an exit selector. The selector is a list of test globs, for example L1.calls: tests/e2e/O0/calls/**, tests/function/abi/**. A unit is complete for an attempt when harness check --impl zig --unit L1.calls passes every test the selector matches and the ratchet holds. The roadmap is shared between attempts, so progress is shown in a table with one row per unit and one column per attempt, generated by harness status.

Why make "done" mechanical?

You said agents push when a unit is "locally verified as complete". With exit selectors, that verification is one command, not a judgement call. Your loop can use the same command to choose the next unit (dependencies met, not yet complete for this attempt), and to notice an agent claiming completion falsely. Writing the selector forces whoever adds a unit to decide up front what "done" means. If an agent finds the unit is too big, it splits it in the roadmap, which is itself a useful signal for a challenge report.

Alternatives:

  1. Units described only in prose, and the agent judges when it's done.
  2. Fixed percentage targets per layer (e.g. "L1 done when 95% of tests/e2e/O0 pass") instead of explicit units.
  3. Units in a machine-readable roadmap.toml, with the Markdown generated from it.

3Each attempt writes its own data-oriented design doc; nothing global gets enforced

AGENTS.md carries only the principle: data-oriented, no OOP. Each attempt's first unit (L0.design, with no tests in its selector) is writing impl/<lang>/DESIGN.md. It covers which of the language's own data-oriented features the attempt uses (Zig's MultiArrayList and comptime, Rust's enums and slices, C's tagged unions and arenas…), the IR's memory layout, and how it reproduces the orders LLVM's output depends on (use-lists, worklists, value-name uniquing). Agents on that attempt must follow it, and they update it when the design changes.

Why write it as a unit, rather than letting the design emerge?

Writing it before the parser exists is cheap. Discovering at InstCombine that use-lists can't be ordered the way LLVM orders them means rewriting layer 0. Making it an explicit unit gives you a natural point to read the three designs side by side before code piles up on them. That's also where the attempts are most interesting to compare.

Alternatives:

  1. No DESIGN.md: each attempt's style lives only in its code.
  2. DESIGN.md is required, but written once layer 0 passes, describing what was actually built.
  3. You review each DESIGN.md before that attempt continues past L0.design.

4Python harness, live oracle cached in /persistent, and a passing list per attempt (carried over from round 2's proposal 4, revised)

harness/ is plain Python 3 (standard library only). LLVM's outputs are computed live and cached by a hash of (input, command, LLVM version). The cache lives in /persistent/llvm-rewrite/oracle-cache/, written atomically (write to a temp file, then rename), so every workspace and agent shares it and LLVM is only ever run once per input. Each attempt has a sorted impl/<lang>/passing.txt: harness check fails if a listed test fails, and --update adds new passes. On a merge conflict: take the union, then re-run.

Why Python, and why put the cache in /persistent?

The harness has to be neutral between the attempts and readable by every agent. All it does is orchestrate subprocesses, so it needs no build, and it has no dependencies to install. With many workspaces each running the full check before pushing, an oracle cache per workspace would run LLVM again for every test in every new workspace. The cache in /persistent is shared by every workspace from this template. Because the key includes the LLVM version, it can never serve a stale answer.

Alternatives:

  1. Write the harness in Rust.
  2. One status.tsv with a column per attempt.
  3. A cache per workspace in .cache/ (fully isolated, but slower first runs).

5Tests grouped by kind and area; imported LLVM tests keep their original path

tests/roundtrip/…                 L0: parse → print must equal llvm-dis
tests/pass/<pass>/…               written by agents; RUN gives the pass
tests/imported/llvm/Transforms/<Pass>/…   LLVM's tests, original path kept
tests/e2e/{O0,O2}/<area>/…        each has a .c file next to the .ll
tests/function/<area>/…          .ll function + driver.c

Rules for e2e: the program must be deterministic and self-contained, with no stdin, no arguments and no time or address dependence, and a 10 s timeout. Stdout and exit code are compared. The importer only keeps RUN lines that are target-independent or x86, with flags we support, and writes every file or RUN line it skips (with the reason) to tests/imported/SKIPPED.md.

Why keep the original path for imported tests?

An agent porting InstCombine/select.ll can jump straight from our failing test to LLVM's file and its git history, which usually explains why a transform exists. Re-importing at a newer LLVM version also becomes a clean diff. SKIPPED.md is the to-do list for widening the importer later, and it stops tests from silently disappearing.

Alternatives:

  1. Group by layer first (tests/L3/instcombine/…).
  2. Rewrite imported tests into our own naming, and record where each came from in a comment in the file.
  3. Also compare stderr in e2e tests.

6The workspace image bakes in LLVM 23.1.5, its source, and llvm-test-suite

.agents-in-the-cloud/Dockerfile (FROM agents-in-the-cloud-workspace) installs zstd, zig (pinned) and the Rust toolchain if the base image lacks them. It then downloads LLVM-23.1.5-Linux-X64.tar.zst, checks it against a sha256 pinned in the Dockerfile, and unpacks it to /opt/llvm-23.1.5. It makes a shallow clone of llvm-project at llvmorg-23.1.5, keeping only llvm/, to /opt/llvm-project-23.1.5, and clones llvm-test-suite at its matching tag. The harness hardcodes those paths, so no environment variables are needed. Changing the version means editing one Dockerfile line and the one constant in the harness.

Why bake it into the image rather than into /persistent?

The Dockerfile is the documented way to customise workspaces. It's reproducible from the repo, and AgentsInTheCloud rebuilds the image only when the Dockerfile changes, so every new workspace starts with LLVM ready and no download. /persistent would also work, but it's mutable shared state that nothing versions. I'll unpack everything first, then measure. If the image is too big, I'll prune the tarball to the tools the harness uses plus clang's resource headers.

Alternatives:

  1. Prune the tarball from the start (smaller image, but we may find out the hard way which tools we need).
  2. Source checkout without llvm/test in the image (the importer clones it when it needs it).
  3. Leave out llvm-test-suite until layer 1 actually needs it.

7Three places for notes: knowledge about LLVM, notes per attempt, and challenge reports for you (carried over from round 2's proposal 6)

knowledge/llvm/<area>.md          facts about LLVM behaviour, shared by all attempts
impl/<lang>/NOTES.md              findings specific to one attempt or language
reports/challenges/<date>-<lang>-<slug>.md   one file per challenge, for you

Knowledge files are organised by topic, and agents curate them (correcting or deleting stale claims rather than only appending). Agents read the relevant topic before starting work in that area. Challenge reports are about the process, not the compiler. Each has the fields what happened · time/effort lost · what would have helped, and an agent writes one before pushing whenever something got in its way.

Why one file per challenge but one file per topic for knowledge?

Many agents write challenge reports at the same time, and one file per report never conflicts on rebase. You can sort and grep them by date and attempt when you tune your loop. Knowledge is meant to be curated, and grouping by topic is what makes it findable. When a topic settles, it can be promoted into a skill.

Alternatives:

  1. One file per finding for knowledge too.
  2. Single append-only FINDINGS.md and CHALLENGES.md at the root.
  3. Add reports/units/: a short summary of each completed unit (time taken, tests moved), giving your loop a progress log.
