1Port LLVM faithfully, with LLVM 21.1.8 as the fixed oracle

We port LLVM's algorithms one pass at a time from the C++ source, and treat LLVM 21.1.8 (Ubuntu's llvm-21 packages, the same version as the clang already installed here) as the source of truth. A script fetches a sparse checkout of llvm-project at llvmorg-21.1.8 into a gitignored third_party/ folder, so every agent can read the pass it's porting. Our data structures can differ from LLVM's. What our code does can't.

Why not a clean-room design?

Your plan to "test our correctness against a single pass" only works if our pass does what LLVM's pass does, heuristic choices included: which InstCombine rewrite fires first, the inliner's cost thresholds, which leader GVN picks. A clean-room design would produce IR that's different but still valid. Then every IR→IR test would need a semantic equivalence checker instead of a plain diff.

Porting also gives agents bounded tasks: "port lib/Transforms/Scalar/EarlyCSE.cpp" comes with an obvious reference. Pinning matters because pass output changes between LLVM releases, so the harness refuses to bless goldens produced by any other version. LLVM's license (Apache-2.0 with the LLVM exception) allows a port as long as we credit it.

Alternatives:

  1. Clean-room redesign, using LLVM only to check behaviour: lots of freedom, but per-pass tests get much weaker (e2e plus semantic equivalence only).
  2. Track LLVM main instead of a release: newer, but the goldens would keep changing under us.
  3. Build LLVM 21.1.8 from source with assertions on, and use that as the oracle: gives -debug-only= traces and stricter verification for about an hour of build time. Could be added later.

2Two oracles: run e2e programs and compare behaviour; diff pass output exactly

e2e: we and LLVM (llc) each compile the IR, clang links both, and both programs run. Stdout and exit code must match. The assembly doesn't have to match. One variant is the function test: we compile a single IR function and link it with a C driver built by clang, which calls it with many inputs. That checks ABI compatibility directly.
pass (IR→IR): the same input goes through opt -passes=… and through our tool. Both outputs are canonicalized with llvm-as | llvm-dis, and the results must be identical.

Why not byte-identical assembly?

To match llc byte for byte, we'd have to copy every quirk of FastISel, RegAllocFast, the scheduler and the asm printer before a single program runs. It would also rule out ever improving on LLVM's codegen. Running the program checks what actually matters and leaves the backend free.

For IR passes the trade-off flips. A single pass is small enough to replicate exactly, and an exact diff is the sharpest way to catch edge cases. Canonicalizing through LLVM's own assembler and disassembler means value numbering, attribute groups and metadata order can't cause false failures, so pass work doesn't have to wait for a perfect printer.

A UB guard: each e2e program is also built with clang -O0 and clang -O2. If those two builds behave differently, the program has undefined behaviour and the test is rejected.

Alternatives:

  1. Require exact asm matches for -O0 codegen (a port of FastISel and RegAllocFast) and compare behaviour only from -O1 up.
  2. Check pass tests for semantic equivalence with Alive2: proves our output is a valid refinement and accepts different-but-correct results. It's a heavy dependency (z3 plus LLVM dev headers). Worth adding later for any pass where we diverge on purpose.
  3. FileCheck-style CHECK lines like LLVM's own tests: partial matching only. It's weaker, and it's easy for an agent to write checks that pass trivially.

3Rust, in a cargo workspace whose crates follow LLVM's layers

Crates: ir (types, values, module, .ll parser, printer, verifier), analysis (dominators, loops, alias analysis, SCEV, MemorySSA), transforms (one module per pass, named like LLVM's), codegen (machine IR, register allocation, frame lowering), target-x86, tools (the binaries) and harness. The IR uses arenas with typed IDs (ValueId, InstId, BlockId) and explicit use-lists. We settle that once, at layer 0, in docs/architecture.md.

Why not C++, which would make porting easiest?

C++ would allow near line-by-line porting. But an IR that's constantly being mutated is exactly where memory bugs turn into silent miscompiles, and with many agents writing code we want those caught at compile time. Rust 1.98 is already installed, and cargo gives us workspaces, parallel tests and benchmarks for free.

The cost is that LLVM's pointer graph doesn't translate directly. We use arenas and indices instead, and port idioms like replaceAllUsesWith and the intrusive instruction lists by hand. That's why this decision belongs in layer 0, before any pass is written.

Alternatives:

  1. C++20: closest to the source, quickest to port, but prone to segfaults and UB.
  2. Zig: simple and fast to compile, with less agent training data and a less mature ecosystem.
  3. Jai: you've used it before, but agents have very little training data for it and there's no public toolchain for CI.

4One target: x86-64 SysV Linux, emitting textual assembly

We target x86_64-unknown-linux-gnu and emit AT&T-syntax .s, which system clang assembles and links against glibc. Input is textual .ll only: no bitcode, no object emission, and no other targets until the -O2 pipeline passes.

Why not AArch64 too, or emit object files?

This container is x86-64, so tests run natively without qemu. Textual assembly is what you asked for, and it can be debugged just by reading it. The MC layer (assembler, ELF writer) is a big project of its own and adds nothing to codegen correctness. Keeping target-specific code inside target-x86 means a second target can be added later without touching the rest.

Alternatives:

  1. Add AArch64 from the start, with tests running under qemu-user.
  2. Emit ELF objects directly by porting the MC layer.
  3. Also accept bitcode (.bc) input.

5Same command line as opt, llc and llvm-link

Our tools accept LLVM's flags for whatever subset we implement: ropt -passes='instcombine,gvn' -S in.ll -o out.ll, rllc -O0 in.ll -o out.s, rlink a.ll b.ll -S -o all.ll. ropt -O2 -print-pipeline-passes prints exactly what opt prints. Whole-program optimization means linking all modules into one with rlink, then running ropt -passes='lto<O2>', the same way LLVM's full LTO works.

Why copy LLVM's command line?

The harness runs the same command line against both toolchains and only swaps the binary, so test files can quote LLVM's own RUN lines unchanged. Pipelines become data: we can implement the O2 pipeline in exactly LLVM's pass order. When a whole-pipeline test fails, a harness bisect command runs longer and longer prefixes of the pipeline through both tools and reports the first pass where the outputs differ. That turns "-O2 is broken" into "pass 37 (jump-threading) is wrong on this input".

Alternatives:

  1. Our own CLI and library API, with a harness adapter for each tool.
  2. ThinLTO-style, summary-based whole-program optimization instead of full LTO: scales to big programs, but is much more complex.
  3. One binary with subcommands (rl opt …), using the same flags. Purely cosmetic.

6One test per file, checked-in goldens, and a ratchet

A test is a .ll file with a short header, plus a sibling .expected file that harness bless generates from LLVM 21.1.8 and that gets checked in:

; KIND: pass            (or: e2e, function, roundtrip)
; RUN: -passes=instcombine
; STATUS: pending       (or: passing)

The harness fails CI if any passing test fails. Agents add new tests as pending. Making progress on a test means getting it to pass and flipping it to passing in the same commit. harness status prints the scoreboard: passing and pending counts per layer and per pass.

Why checked-in goldens and a ratchet?

With goldens checked in, each test explains itself: an agent can see exactly what LLVM produces without running anything. Test runs stay fast and parallel, and harness verify-goldens regenerates every golden and diffs it, which catches oracle drift.

The ratchet is what lets many agents work at once. Nobody can quietly regress someone else's progress, and the passing count only goes up. Pending tests are a normal part of the suite, so "write a test, then make progress on it" is the default workflow. Keeping status in each test file (not a central list) avoids merge conflicts, because agents usually work on different tests.

Alternatives:

  1. Compute the oracle live at test time, with no goldens: simpler, but slower and sensitive to whatever LLVM version is installed.
  2. Use LLVM's lit + FileCheck as the runner: familiar, but it adds little when the oracle is a diff against a golden.
  3. One central passing.txt list instead of in-file status: easier to scan, but a constant source of merge conflicts.

7Tests come from four sources, with LLVM's own test suite as the main source for passes

  1. Agent-written C snippets, compiled to IR with clang -O0 -Xclang -disable-O0-optnone -S -emit-llvm, and also at -O1/-O2 because optimized IR uses constructs that unoptimized IR doesn't (phis, selects, vectors). The .c file sits next to the .ll for readability, but the test itself is the IR.
  2. LLVM's regression tests in llvm/test/Transforms/<Pass>/*.ll, imported by a script as pass tests. We take the passes from their RUN line, ignore their CHECK lines, and use opt's output as the golden.
  3. llvm-test-suite SingleSource programs, compiled to IR and used as e2e tests.
  4. Later: Csmith/YARPGen random programs for differential fuzzing. Failures get minimized with llvm-reduce and land as new pending tests.
Why lean on LLVM's own test suite?

For each pass, LLVM's Transforms tests are already the "tests designed to target that layer" you described, chosen by the people who wrote the pass. InstCombine alone has well over a thousand test files. Importing them gives us most of each pass's test set for free, and agents fill the gaps with their own tests.

The -disable-O0-optnone flag matters. Without it, clang's -O0 IR is marked optnone and opt skips most passes.

Alternatives:

  1. Hand-written tests only: smaller, every test understood, much less coverage.
  2. Fuzz from day one: finds bugs fast, but lots of noise before the basics work.
  3. Also import llvm/test/CodeGen/X86: those are asm FileCheck tests that don't fit the run-and-compare oracle, so they're mostly useful as reading material.

8Build it in six layers

  1. IR core: parser, printer, verifier. Test: every .ll in the corpus round-trips identically to llvm-as | llvm-dis.
  2. -O0 codegen: straightforward per-instruction lowering, every value spilled to the stack, a simple local register allocator, the SysV calling convention and frame lowering. Tests: e2e and function tests on -O0 IR.
  3. Codegen for optimized IR: phis, selects, switches, vectors/SSE, common intrinsics. Tests: e2e on -O2 IR produced by clang.
  4. Analyses + scalar passes, in the order the O2 pipeline needs them: sroa/mem2reg, simplifycfg, early-cse, instcombine (split up by instruction family), gvn, licm, loop passes, dse, sccp, jump-threading… Analyses are tested with opt -passes='print<domtree>' and similar, using the same diff oracle.
  5. IPO / whole program: inliner, globalopt, ipsccp, function-attrs, argpromotion, deadargelim, globaldce, internalize, and the full lto<O2> pipeline.
  6. Backend optimization: a real instruction selector, greedy register allocation, scheduling, peepholes. Measured by benchmarks against llc -O2, not by exact matches.

Every new pass gets its imported LLVM tests, its agent-written tests, and a run of the whole e2e suite with the pass turned on. Which instruction-selection design to use is a decision for a later round.

Why not optimizations first, or an interpreter first?

Layer 0 underpins everything else. Layer 1 makes e2e tests work early, and from then on every IR pass we add is also checked by running real programs (our pass → our backend → run), not just by IR diffs. Analyses go into layer 3 because almost every pass depends on them, and their print passes give us exact oracles for free.

Alternatives:

  1. Build an IR interpreter (like lli) before codegen: gives a way to execute IR that doesn't depend on our backend, so semantics can be checked after any pass. The cost is a second executor to maintain.
  2. All IR passes first, codegen last: pass work starts sooner, but there's no e2e signal for a long time.
  3. Structure -O0 codegen like GlobalISel from the start (IRTranslator, Legalizer, RegBankSelect, InstructionSelect), so it grows into layer 5 instead of being rewritten.

9Agent instructions: a short AGENTS.md plus task skills

AGENTS.md (with a CLAUDE.md symlink) covers the goal, the repo layout, the golden rule ("LLVM 21.1.8 is always right"), how to run the harness, and the ratchet rule. Skills live in .agents/skills/ next to lplan:

  • write-test: write a C or IR test, bless it, add it as pending.
  • port-pass: read the LLVM source, import its Transforms tests, implement, flip tests to passing, run e2e with the pass on.
  • debug-mismatch: pipeline bisect, then llvm-reduce with our tool as the interestingness test, then land the reduced case as a new test.
  • codegen: backend conventions, SysV ABI checklist, how to compare our asm with llc's.

Plus a single docs/architecture.md on the IR data structures, which agents read before touching ir.

Why skills rather than one big document?

Most agents will be doing one of four kinds of task. A skill gives each of them a precise, step-by-step loop without loading the rest into context. AGENTS.md stays short enough that every agent actually reads it. Skills are also the natural place to record lessons learned ("InstCombine tests depend on the order of the worklist; see …").

Alternatives:

  1. One long AGENTS.md.
  2. An AGENTS.md per crate, with local rules next to the code.
  3. Skills only, no AGENTS.md.

10Coordinate work with GitHub issues, PRs and CI

Coarse work items ("port EarlyCSE", "L1: calls with struct args") are issues on lucasmeijer/llvm-rewrite, labelled by layer and pass. An agent claims an issue by assigning it, works on a branch, and lands a PR that GitHub Actions must pass (full harness plus ratchet, with LLVM 21 from apt.llvm.org). Finer-grained work items are just the pending tests.

Why not an in-repo task board?

An in-repo board makes every claim a commit, so claims race and conflict. Issues give us atomic claiming, a discussion thread, and somewhere to record blocked work. CI on PRs is what enforces the ratchet when many agents land work in parallel. Without it, the ratchet only holds if every agent remembers to run it.

Alternatives:

  1. In-repo tasks/*.md with claimed-by fields, everyone pushing straight to main.
  2. No explicit coordination: agents pick pending tests, and the scoreboard is the plan.
  3. One orchestrator agent assigns work to sub-agents that share a single workspace.
